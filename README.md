# tg-agent-mcp

Telegram-инструмент Claude Code: MCP-сервер даёт агенту руки в Telegram, демон
делает долгую работу.

Возможности добавляются группами инструментов. Сейчас их две поверх одной живой
сессии. Доставка кампаний: на вход приходит готовый список получателей и текст,
дальше сервис сам держит темп, окно отправки, дневной потолок и стоп аккаунта,
пока не отдаст всё или не упрётся в ограничение. Диалоги: найти человека,
написать ему руками, прочитать переписку - только личка и только текст; список
диалогов шире переписки и показывает ещё группы и каналы аккаунта.

Сервис не решает, кому писать. Список собирает вызывающий и передаёт
инструментом; откуда он взялся и зачем эта рассылка, сервису неизвестно. Задача
и критерии отбора живут в отдельном проекте рассылок.

**Кампания** - один заход рассылки: шаблон текста и список получателей,
загруженные инструментами `load_campaign` и `add_recipients`. Дальше сервис
ведёт её сам: очередь, темп, окно отправки, отсев тех, кому уже писали,
остановка при ограничении аккаунта. Активная кампания в системе одна, и
аккаунты делят её очередь; состояния - черновик, работа, пауза, отмена,
завершение, - и текущее называет `status`.

## Инструменты

| Инструмент | Что делает |
| --- | --- |
| `load_campaign` | проверяет шаблон и создаёт черновик кампании, отменяя прежний |
| `add_recipients` | добавляет получателей пачкой до 50, отдаёт отчёт об отсеве |
| `start` | переводит черновик в работу, он же продолжает кампанию с паузы |
| `stop` | пауза кампании или отмена вместе с очередью - по флагу `cancel` |
| `resume_account` | снимает стоп аккаунта - только руками человека |
| `status` | состояние кампаний и аккаунтов, причина простоя очереди |
| `tg_find` | ищет человека: точный ник резолвит через Telegram, имя - среди контактов и своих диалогов |
| `tg_send` | пишет в личку руками, записывает касание в журнал |
| `tg_read` | показывает диалог и, если попросили, ждёт чужую реплику |
| `tg_dialogs` | список диалогов с непрочитанными: у каждой строки назван вид - человек, группа, канал |

Транспорт - streamable HTTP за bearer-токеном, официальный
`modelcontextprotocol/go-sdk` v1. Второй токен `MCP_AGENT_TOKEN` - агентский
доступ: видны только `tg_send` и `tg_read`, и только к никам из
`AGENT_ALLOW_LIST`; другой ник отклоняет сервис. Этим доступом агенты проверяют
ботов без подтверждения владельца.

## Рубежи

Это главное, что делает сервис, и причина, по которой он существует отдельно от
скрипта отправки:

- одно сообщение на человека - за кампанию и между кампаниями, включая
  написанное руками через `tg_send`, перезапуски и повторный старт;
- в отправку не идёт получатель без пригодного ника Telegram, а под шаблоном с
  `{имя}` - и получатель с фигурной скобкой в имени: она уехала бы в письмо;
  пустое имя отсевом не является - письмо уходит без обращения и без запятой;
- письмо с неразобранной фигурной скобкой не уходит вовсе: шаблон отбивается на
  входе, а у кампании, собранной прошлой версией, очередь встаёт - саму кампанию
  сервис не трогает, её собирают заново, и о простое говорят `status` и ERROR;
- окно 10:00-19:00 по будням и дневной потолок держат рассылку и первое
  касание незнакомца; реплика в идущем диалоге им не подчиняется намеренно -
  запрет ответить в 21:30 делает аккаунт менее похожим на живой, а не более;
- ограничение аккаунта (`PEER_FLOOD`, длинный `FLOOD_WAIT`) останавливает этот
  аккаунт целиком и снимается только человеком, никогда по таймеру;
- стоп одного аккаунта не трогает соседние и не рушит кампанию;
- счётчики, паузы, стопы и сам потолок живут в БД, а не в памяти: иначе рестарт
  в цикле обходит любой потолок;
- молчание очереди наблюдаемо: `status` называет причину простоя с числами -
  закрытое окно и час открытия, израсходованный потолок, стоп аккаунта, чужие
  строки, сломанный шаблон, - а не оставляет её одному логу.

## Запуск

```bash
cd src
docker compose up -d          # postgres:16 на порту 5433
make ci-check                 # миграции, тесты, vet, fmt, lint, build
make test-fast                # быстрый ярус без БД
```

Полный прогон требует `DATABASE_URL` отдельно от `TEST_DATABASE_URL` - защита
от миграции не в ту базу.

Конфигурация: обязательны `DATABASE_URL` и `ACCOUNT_LABEL`; `MCP_ENABLED`
включает сервер управления (по умолчанию выключен), при включённом обязателен
`MCP_TOKEN`, адрес - `MCP_ADDR` (`:8080`). `ACCOUNT_DAILY_LIMIT` задаёт дневной
потолок только при создании строки аккаунта: дальше потолок живёт в БД,
действующее число печатает `status`, а расхождение с переменной сервис называет
предупреждением при старте. `TRANSPORT=live` вне `ENV=prod` не поднимается:
процесс отказывается стартовать, чтобы живая отправка не ушла с проверочного
контура. Отправщик может работать с выключенным MCP: управление и
доставка разносятся по экземплярам.
