# Первый живой запуск

Порядок действий с момента, когда заказчик отдал Telegram-аккаунт, до первого
сообщения живому человеку. Пройден 03.09.2026 на аккаунте `@sender_account`;
дальше он служит порядком для следующего аккаунта.

## Где живёт сервис

На машине владельца, в Docker (решение владельца 02.09.2026). Своего адреса в сети у
сервиса нет, отправка идёт с домашнего IP, рассылка живёт, пока включена
машина.

## 1. Что нужно получить от заказчика

Закрыто 03.09.2026, для следующего аккаунта нужен тот же набор:

| Что | Зачем |
| --- | --- |
| номер аккаунта | вход в сессию, `TELEGRAM_PHONE` |
| доступ к коду входа | Telegram присылает код в приложение; без него сессию не завести |
| подтверждение прогрева | пустой номер, начавший писать незнакомым, банится на первой рассылке |
| пароль двухфакторки, если включена | иначе вход остановится на середине |

Аккаунт нужен рабочий и живой, а не свежекупленный: единственное наблюдение
портфеля (`services/telegram.md`, 29.08.2026) - ограничение прилетело при 2-3
сообщениях в день, то есть темпом оно не объясняется.

`api_id` и `api_hash` берутся на my.telegram.org под тем же номером и живут в
`TELEGRAM_APP_ID` и `TELEGRAM_APP_HASH`. Ключи чужого аккаунта работать будут,
но привязка «приложение к номеру» - то, что видит Telegram, и разнобой здесь
лишний.

## 2. Контур

Настройки - `src/.env` по образцу `src/.env.example`; файл в гит не попадает.
Пароль базы и токен MCP лежат в Keychain (`tg-agent-mcp/postgres`,
`tg-agent-mcp/mcp`). `ENV` контура уже `prod` (дефолт compose), менять
его не нужно: `TRANSPORT=live` вне `ENV=prod` валит старт бинаря.

```
cd src
make live-up        # postgres, миграции, приложение; MCP на 127.0.0.1:8087
make live-logs      # что происходит
make live-down      # остановить
```

Claude Code берёт эндпоинт из `.mcp.json` проекта `campaigns`. Токен
приходит из окружения, поэтому в `~/.zshrc`:

```
export TG_AGENT_MCP_TOKEN=$(security find-generic-password -s tg-agent-mcp/mcp -a MCP_TOKEN -w)
```

Проектный `.mcp.json` требует одобрения при первом запуске `claude` в каталоге
`campaigns` - это защита от чужого репозитория, а не ошибка.

## 3. Вход в аккаунт

Вход - разовая ручная операция с терминала: код приходит в Telegram, ввести его
может только человек.

```
cd src
make live-authorize
```

Команда не читает ни базу, ни конфиг сервиса - только переменные `TELEGRAM_*`.
Она спросит код, при двухфакторке - пароль, и напечатает, кем вошла:

```
authorized: Club @sender_account (id <id>, phone <номер>)
```

Что важно знать:

- **Сессию держит один процесс.** Пока отправщик работает в `TRANSPORT=live`,
  файл сессии заперт, и вход скажет «storage is locked by another process».
  Вход делается на контуре в `dry-run` - в этом режиме Telegram не открывается
  вовсе. Контур после первого запуска стоит в `live`, поэтому перед повторным
  входом вернуть `TRANSPORT=dry-run` и поднять контур заново либо остановить
  `app`.
- **Чужая сессия в хранилище отвергается.** Если в томе уже лежит сессия
  другого номера, вход не идёт вовсе, а не проходит молча: иначе рассылка ушла
  бы не с того аккаунта.
- Номер в выводе обязан совпасть с тем, который дал заказчик. Не совпал -
  разбираться, а не запускать.

## 4. Проверка перед живой отправкой

- `curl -s http://127.0.0.1:8088/health` отвечает `ok`;
- `status` через MCP отвечает и показывает аккаунт с меткой из `ACCOUNT_LABEL`;
- в логе есть `service started`, и поле `transport` совпадает с режимом контура.

## 5. Пилот на своих

Перед первой кампанией - несколько сообщений людям, которые об этом знают. Это
единственный способ увидеть живой резолв ника, закрытую личку и настоящие коды
ошибок MTProto: до этого транспорт проверялся только тестами.

Пройден 03.09.2026: два сообщения (свой аккаунт и бот-квалификатор), оба
доставлены с первой попытки, ответы распознаны, кампании закрылись сами.
Закрытая личка и отказы MTProto так и не встретились - их поведение проверено
только тестами.

Порядок для следующего аккаунта:

1. в `src/.env`: `DEV_ALLOW_LIST=<ники своих>` - список работает и в живом
   режиме, несмотря на имя переменной: это последний рубеж, и он не зависит от
   транспорта;
2. там же `TRANSPORT=live`, затем `make live-up` (пересоздаст контейнер);
3. кампания на этих людях через MCP: `load_campaign`, `add_recipients`, `start`;
4. в логе смотреть `message sent` на каждую отправку, `recipient replied` на
   ответ и `sender idle` с полем `reason`, когда очередь молчит.

Аккаунт словил ограничение уже на пилоте - остановиться и разговаривать с
заказчиком: рассылать с такого аккаунта нельзя.

## 6. Первая кампания

`DEV_ALLOW_LIST` очистить, `make live-up`, дальше по скиллу `campaign` в
отдельном проекте рассылок: список собирается там, сюда приходит
готовая пачка.

Перед стартом кампании - `make live-dump`. В базе лежит знание, кому уже
писали; это единственный рубеж «один человек - одно сообщение» между
кампаниями, и другого его экземпляра нет.

Наблюдение - `status` в утреннюю и вечернюю сессии. Стоп аккаунта красит
healthcheck и пишет ERROR в лог; снимается только `resume_account` после того,
как человек открыл аккаунт и посмотрел, что с ним.

Аккаунт забанен, а не притормозен - `resume_account` бесполезен: порядок замены
на другой номер вместе с переносом незакрытой очереди - `runbook-account.md`.
Там же порядок правки дневного потолка живого аккаунта.
