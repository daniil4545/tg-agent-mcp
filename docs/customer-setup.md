# Гид: контур tg-agent-mcp на машине заказчика

Порядок с нуля до первой кампании на машине заказчика (macOS, Docker Desktop).
Каждый шаг заканчивается командой и тем, что она обязана напечатать. Вывод не
совпал - это стоп и вопрос владельцу, а не повод идти дальше: сервис пишет
незнакомым людям с живого аккаунта, и цена ошибки здесь равна аккаунту.

## 1. Рамка и результат

В конце на машине заказчика работает свой контур: Postgres с базой кампаний,
приложение с MCP-сервером на `127.0.0.1:8087` и Claude Code, у которого в
сессии есть десять инструментов рассылки и диалогов.

Чем это не является:

- **это не перехват идущей рассылки.** Пилот приглашений до 19.09 ведёт
  владелец со своего контура. Пока пилот не закрыт, контур заказчика работает
  без боевой отправки: он поднимается, проверяется на своих адресатах и ждёт
  передачи аккаунта;
- **это не второй канал того же аккаунта.** Аккаунт передаётся целиком и
  однократно: сначала владелец останавливает свой контур, только потом заказчик
  входит в аккаунт у себя. Порядок - раздел 4;
- **это не копия чужой базы.** База кампаний хранит знание, кому уже писали.
  Пока она не передана, контур заказчика этого знания не имеет.

Запреты, которые не обсуждаются:

1. **Один аккаунт - ровно один контур.** Два процесса на один номер означают
   две независимые очереди и две базы, которые не знают друг о друге, а рубеж
   «один человек - одно сообщение» держится только базой. Результат - два письма
   одному человеку и претензия от него, а не от Telegram.
2. **Чужую живую сессию не поднимать.** Файл сессии не копируется с чужой
   машины. Вход делается заново командой `make live-authorize` после того, как
   владелец остановил свой контур.
3. **Базу владельца не копировать самовольно.** Перенос дампа - решение
   владельца и отдельный шаг передачи, а не действие заказчика.
4. **Боевую отправку не включать до передачи аккаунта.** До неё контур живёт в
   `TRANSPORT=dry-run`, где сообщения пишутся в лог, а не в Telegram.

## 2. Что приготовить заранее

Без любой строки из таблицы вход в аккаунт не пройдёт: `authorize` требует все
четыре переменные `TELEGRAM_*` и падает на первой отсутствующей.

| Что нужно | Зачем | Где взять |
| --- | --- | --- |
| Доступ к репозиторию `daniil4545/tg-agent-mcp` | код контура; обновления забираются `git pull` | владелец даёт доступ на приватный репозиторий GitHub |
| Docker Desktop для macOS, запущенный | контур целиком живёт в контейнерах | docker.com, установка обычная |
| Номер Telegram-аккаунта рассылки | `TELEGRAM_PHONE`, вход в сессию | владелец при передаче аккаунта |
| `api_id` и `api_hash` этого аккаунта | `TELEGRAM_APP_ID`, `TELEGRAM_APP_HASH`; без них клиент не соберётся | владелец передаёт свою пару либо заказчик заводит новую на my.telegram.org, войдя под тем же номером |
| Доступ к коду подтверждения | Telegram присылает код в приложение на этом номере; ввести его может только человек | телефон с активной сессией аккаунта |
| Пароль двухфакторки, если она включена | без него вход остановится на середине | владелец при передаче аккаунта |

Про `api_id` и `api_hash`: пара принадлежит номеру, а не машине. Вывести её
неоткуда, восстановить без доступа к номеру нельзя. Значит, она либо приходит
от владельца вместе с аккаунтом, либо создаётся на my.telegram.org уже после
того, как доступ к номеру у заказчика есть.

## 3. Установка и настройка

Клонировать репозиторий:

```
cd ~
git clone git@github.com:daniil4545/tg-agent-mcp.git
cd tg-agent-mcp
```

Ожидаемо: `Cloning into 'tg-agent-mcp'...` и в конце строка
`Resolving deltas: 100% (...), done.`. Отказ `Permission denied (publickey)`
означает, что доступ к приватному репозиторию ещё не выдан - это вопрос
владельцу, а не повод искать обход.

Проверить инструменты:

```
docker compose version
```

Ожидаемо: строка вида `Docker Compose version v5.3.1`. Команда не найдена или
`Cannot connect to the Docker daemon` - Docker Desktop не установлен или не
запущен.

Собрать настройки:

```
cd ~/tg-agent-mcp/src
cp .env.example .env
```

Файл `.env` в гит не попадает. Заполнить в нём:

| Переменная | Что это | Чем заполняется |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | пароль локальной базы кампаний | любая длинная случайная строка; после создания базы не меняется |
| `MCP_TOKEN` | пароль MCP-эндпоинта, без него сервер отвечает 401 | своя случайная строка, например вывод `openssl rand -hex 32` |
| `ACCOUNT_LABEL` | метка аккаунта, под ней заводится строка в `accounts` | `main`, если владелец передаёт базу кампаний вместе с аккаунтом; иначе своя метка |
| `ACCOUNT_DAILY_LIMIT` | дневной потолок нового аккаунта | 20 - число пилота приглашений |
| `TRANSPORT` | `dry-run` пишет в лог, `live` шлёт в Telegram | `dry-run` до передачи аккаунта |
| `ENV` | `dev` или `prod`; `live` работает только в `prod` | строка `ENV=dev` до передачи аккаунта, `prod` после |
| `DEV_ALLOW_LIST` | служебные адресаты владельца контура | свои ники через запятую на время проверок |
| `DIGEST_ACCOUNT`, `DIGEST_TO` | метка аккаунта, отправляющего вечернюю сводку, и её получатели | пусто до второго отправщика; получатели обязаны быть внутри `DEV_ALLOW_LIST` |
| `TELEGRAM_APP_ID`, `TELEGRAM_APP_HASH`, `TELEGRAM_PHONE` | доступы к аккаунту | из таблицы раздела 2; до передачи аккаунта пустые |
| `MCP_PORT`, `HEALTH_PORT` | порты на петле | оставить 8087 и 8088, если не заняты соседом |

`ACCOUNT_LABEL` важнее, чем выглядит. Строка очереди, однажды взятая аккаунтом,
остаётся закреплённой за ним навсегда. Если владелец передаёт дамп базы, а
метка в `.env` другая, приложение заведёт вторую строку аккаунта, и незакрытые
строки очереди из дампа новому аккаунту недоступны.

Значение `ACCOUNT_DAILY_LIMIT` применяется только при создании строки аккаунта.
У уже существующего аккаунта потолок живёт в базе и меняется запросом -
`runbook-account.md`, раздел 1.

## 4. Первый запуск контура и вход в аккаунт

Поднять контур:

```
cd ~/tg-agent-mcp/src
make live-up
```

Первый запуск собирает образ и занимает несколько минут. В конце команда
печатает:

```
MCP: http://127.0.0.1:8087/mcp
```

Проверить, что поднялись оба контейнера:

```
docker compose -f docker-compose.local.yml ps --format 'table {{.Service}}\t{{.Status}}'
```

Ожидаемо:

```
SERVICE    STATUS
app        Up 5 seconds (healthy)
postgres   Up 20 seconds (healthy)
```

Пометка `healthy` у `app` может появиться не сразу: healthcheck ходит раз в 15
секунд и стартует через 15 секунд после запуска.

Проверить здоровье и лог:

```
curl -s http://127.0.0.1:8088/health; echo
make live-logs
```

Ожидаемо `ok` от `curl` и в логе строки JSON, среди которых:

```
{"level":"INFO","msg":"service started","account_label":"main","transport":"dry-run","mcp_enabled":true,"health_addr":":8081"}
{"level":"INFO","msg":"http listening","addr":":8080"}
{"level":"INFO","msg":"sender started","account":"main"}
{"level":"INFO","msg":"sender idle","account":"main","reason":"no_active_campaign"}
```

Поле `transport` обязано совпадать с тем, что в `.env`. Строка
`sender idle` с причиной `no_active_campaign` означает исправную работу:
кампании ещё нет. Выйти из просмотра логов - Ctrl+C, контур продолжает
работать.

Если в логе есть `daily limit differs from env` - это не ошибка: потолок в базе
отличается от переменной, и действует тот, что в базе. Число из базы называет
`status`.

### Передача аккаунта от владельца

Пока пилот не закрыт, входить в аккаунт нельзя, и дело не в запрете. Одна
сессия MTProto живёт ровно в одном процессе, а рубеж «один человек - одно
сообщение» держится базой кампаний. Два контура на одном номере означают две
базы, которые не видят касаний друг друга, то есть второе письмо одному и тому
же человеку.

Порядок передачи, шаги 1 и 2 делает владелец:

1. Владелец останавливает свой контур: `make live-down` на его машине.
2. Владелец передаёт номер, `api_id`, `api_hash`, пароль двухфакторки и
   решение по базе кампаний: переносится дамп или нет.
3. Заказчик вносит `TELEGRAM_APP_ID`, `TELEGRAM_APP_HASH`, `TELEGRAM_PHONE` в
   `src/.env` и поднимает контур заново: `make live-up`.
4. Заказчик входит в аккаунт (команда ниже). Код подтверждения приходит в
   Telegram на переданный номер, и ввести его должен человек.

`TRANSPORT` на время входа остаётся `dry-run`: в живом режиме файл сессии заперт
работающим отправщиком, и вход откажет.

Вход:

```
cd ~/tg-agent-mcp/src
make live-authorize
```

Команда спросит код, при включённой двухфакторке - пароль, и напечатает, кем
вошла:

```
authorized: Club @sender_account (id <id>, phone <номер>)
```

Номер и ник обязаны совпасть с переданным аккаунтом. Не совпали - остановиться
и разбираться с владельцем.

Отказы и их смысл:

| Текст отказа | Что случилось | Что делать |
| --- | --- | --- |
| `telegram storage ... is locked by another process` | контур работает в `TRANSPORT=live` и держит файл сессии | поставить `TRANSPORT=dry-run`, `make live-up`, повторить вход |
| `telegram storage holds a session of another account (phone ..., expected ...)` | в томе лежит сессия другого номера | это замена аккаунта, а не первый вход: порядок в `runbook-account.md`, раздел 2 |
| `TELEGRAM_APP_ID is required` (и аналоги про `APP_HASH`, `PHONE`) | переменная не заполнена в `.env` | заполнить и повторить; контейнер пересоздаётся `make live-up` |

После успешного входа - живой режим:

1. в `src/.env`: `TRANSPORT=live`, `ENV=prod` (или убрать строку `ENV`, дефолт
   контура уже `prod`);
2. `make live-up`;
3. в логе `service started` с `"transport":"live"`.

## 5. Подключение Claude Code к MCP

Claude Code ходит на эндпоинт с токеном. Токен не кладётся ни в гит, ни в
настройки сессии: он лежит в Keychain, а Claude Code берёт его скриптом
заголовков перед каждым подключением.

Положить токен в Keychain (тот же, что `MCP_TOKEN` в `src/.env`):

```
security add-generic-password -s tg-agent-mcp/mcp -a MCP_TOKEN -w
```

Команда спросит значение и при успехе не печатает ничего. Если запись с таким
именем уже есть, `security` откажет сообщением про существующий элемент
keychain: тогда либо оставить прежнее значение, либо удалить запись
командой `security delete-generic-password -s tg-agent-mcp/mcp` и
завести заново.

Завести рабочий каталог, из которого будет запускаться Claude Code. Он отдельный
от клона намеренно: `git pull` не должен спорить с локальными файлами.

```
mkdir -p ~/tg-agent/scripts
cd ~/tg-agent
```

Файл `~/tg-agent/.mcp.json`:

```
{
  "mcpServers": {
    "tg-agent": {
      "type": "http",
      "url": "http://127.0.0.1:8087/mcp",
      "headersHelper": "./scripts/mcp-headers.sh"
    }
  }
}
```

Файл `~/tg-agent/scripts/mcp-headers.sh`:

```
#!/usr/bin/env bash
set -euo pipefail

token="$(security find-generic-password -s tg-agent-mcp/mcp -a MCP_TOKEN -w 2>/dev/null || true)"

if [[ -z "$token" ]]; then
    echo "нет записи tg-agent-mcp/mcp в Keychain" >&2
    exit 1
fi

printf '{"Authorization": "Bearer %s"}\n' "$token"
```

Сделать его исполняемым и проверить, что эндпоинт закрыт без токена:

```
chmod +x ~/tg-agent/scripts/mcp-headers.sh
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8087/mcp
```

Ожидаемо `401`: без токена сервер не отвечает никому, и это рубеж, а не сбой.

Проверить подключение:

```
cd ~/tg-agent
claude mcp list
```

Ожидаемо строка `tg-agent: http://127.0.0.1:8087/mcp (HTTP)` с пометкой
`Pending approval (run claude to approve)` при первом запуске. Проектный
`.mcp.json` требует одобрения человеком - это защита от чужого репозитория, а
не ошибка. Запустить `claude` в этом каталоге, одобрить сервер, затем повторить
`claude mcp list`: пометка сменится на подключённый.

Внутри сессии Claude Code проверка одна: список инструментов обязан содержать
десять имён - `load_campaign`, `add_recipients`, `start`, `stop`,
`resume_account`, `status`, `tg_find`, `tg_send`, `tg_read`, `tg_dialogs`.
Инструментов нет - расходятся токен в Keychain и `MCP_TOKEN` в `src/.env`.

## 6. Проверка на себе до первого живого письма

Проверка идёт двумя заходами: сначала без Telegram вовсе, потом на своих никах.

**Заход первый, до передачи аккаунта.** В `src/.env`: `ENV=dev`,
`TRANSPORT=dry-run`, `DEV_ALLOW_LIST=<свои ники через запятую>`, затем
`make live-up`. В этом сочетании наружу не уходит ничего: живого Telegram нет, а
список в `dev` работает последним рубежом транспорта.

Через Claude Code:

1. `load_campaign` с названием и шаблоном, например `Привет, {имя}! Это
   проверка контура.`;
2. `add_recipients` с одной записью: свой `contact_id` (любое число),
   `name` и `username` своего ника;
3. `start`.

Ожидаемо в ответе `add_recipients` первая строка `Принято: 1 из 1.`, а в логе
через минуту-другую:

```
{"level":"INFO","msg":"dry-run send","username":"<ваш ник>","random_id":...,"text":"Привет, ..."}
```

Строка `dry-run send` означает, что цепочка целиком собрана: кампания, очередь,
рубежи, отправщик. В Telegram при этом не ушло ничего.

**Заход второй, после передачи аккаунта.** `TRANSPORT=live`, `ENV=prod`,
`DEV_ALLOW_LIST` со своими никами, `make live-up`. Та же кампания на свой ник, и
сообщение обязано прийти в Telegram, а в логе появиться:

```
{"level":"INFO","msg":"message sent","username":"<ваш ник>",...}
```

Здесь важно понимать рубеж честно: **в `prod` список `DEV_ALLOW_LIST` не
запрещает писать посторонним.** В `prod` он делает ровно одно - снимает окно,
дневной потолок и правило «одно сообщение» для перечисленных ников, чтобы
проверки не тратили квоту. Единственное, что ограничивает адресатов боевой
кампании, это список, который загрузили в `add_recipients`. Проверять на себе
значит класть в кампанию только свои ники.

Критерий «можно идти дальше»: сообщение пришло в Telegram, в логе есть
`message sent`, `status` показывает кампанию и строку аккаунта с потолком из
базы. Перед настоящей кампанией `DEV_ALLOW_LIST` очищается и делается
`make live-up`.

## 7. Первая настоящая кампания

Перед стартом - дамп базы. В ней единственный экземпляр знания, кому уже
писали:

```
cd ~/tg-agent-mcp/src
make live-dump
```

Ожидаемо последняя строка вида
`-rw-r--r-- 1 user staff 45K ... campaigns-20260908-1030.sql`. Каталог
`backups/` в гит не попадает: там имена и ники живых людей.

Дальше три инструмента по порядку.

1. **`load_campaign`** - название и шаблон. `{имя}` заменяется на имя
   получателя; других подстановок нет, и любая другая фигурная скобка в тексте
   отобьётся отказом. Прежний черновик при этом отменяется.
2. **`add_recipients`** - пачка до 50 человек за вызов, у каждого обязательны
   `contact_id`, `name`, `username`. Больше 50 - несколько вызовов подряд.
3. **`start`** - черновик уходит в работу. Ответ называет id кампании и окно
   отправки, например: `Кампания запущена (id 25). Отправка идёт в окно
   10:00-19:00 по будням, не больше дневного потолка аккаунта.`

Отчёт `add_recipients` начинается со строки `Принято: N из M.`, и если кого-то
отсеяли, следом идут причины с числами. Причины и их смысл:

| Причина в отчёте | Что она значит |
| --- | --- |
| `нет пригодного ника Telegram` | ника нет или он не по форме: 5-32 символа, латиница, цифры и подчёркивание |
| `нет id контакта amoCRM` | в записи нет `contact_id` |
| `дубль: уже в кампании или дважды в пачке` | этот контакт в кампании уже есть |
| `стоп-лист` | человеку не уходит ничего и никогда, ни кампанией, ни руками |
| `уже получал сообщение` | ему писала эта или прошлая кампания |
| `уже писали руками через tg_send` | касание из журнала ручных отправок |
| `писали руками, доставка неизвестна` | ручное касание, по которому Telegram не подтвердил исход |
| `в имени фигурная скобка, она уедет в письмо` | имя испортит текст письма |
| `письмо с его именем длиннее предела Telegram` | шаблон вместе с именем не помещается |

Отсев - это рубеж, а не придирка: каждая снятая строка означает человека,
которому письмо ушло бы вторым.

Дальше кампания идёт сама. Темп задан двумя рубежами: окно 10:00-19:00 по
будням и дневной потолок аккаунта. Пауза между витками отправщика случайная,
10-30 минут, поэтому первое письмо уходит не в секунду `start`, а в пределах
получаса, и 20 писем растягиваются примерно на 6 часов 20 минут. Порция, не
уместившаяся в день, уходит на следующий будний день: очередь не теряется.

## 8. Ежедневное наблюдение

Инструмент `status` утром и вечером - весь регламент. Он печатает кампанию со
счётчиками, строку аккаунта с расходом потолка и, если очередь стоит, причину
простоя словами и числами. Пример живого ответа:

```
Кампания: Пилот приглашений (id 25), статус active.
Строк всего: 40, отправлено 12
Аккаунты:
  main: сегодня 12 из 20 (потолок из БД, с учётом строк в работе)
```

Аккаунтов может быть несколько (раздел 10). Тогда строка есть у каждого, и
причина молчания стоит там же - у того аккаунта, к которому относится:

```
Аккаунты:
  main: сегодня 20 из 20 (потолок из БД, с учётом строк в работе), молчит: дневной потолок аккаунта израсходован (20 из 20)
  second: сегодня 6 из 20 (потолок из БД, с учётом строк в работе)
```

Общая причина - закрытое окно, отсутствие кампании, пустая очередь - остаётся
одной строкой на всех: она у аккаунтов одна и та же.

Девять причин простоя и что с ними делать:

| Причина в отчёте | Что значит | Действие |
| --- | --- | --- |
| окно отправки закрыто, ближайшее открытие ... | ночь, выходные или вне 10:00-19:00 | ничего, откроется само |
| дневной потолок аккаунта израсходован (N из M) | порция дня выбрана | ничего, продолжится завтра |
| аккаунт остановлен | Telegram ограничил аккаунт | стоп, раздел 9 |
| идущей кампании нет - запустите её через start | черновик или пауза | `start` |
| кампания закрыта, новую создаёт load_campaign | работать не над чем | новая кампания |
| шаблон идущей кампании не разобран | в тексте лишняя фигурная скобка | собрать кампанию заново |
| очередь пуста: строк в работе не осталось | всё отправлено | ничего |
| оставшиеся строки закреплены за другим аккаунтом | их отправит тот аккаунт, который их взял | ничего, если он жив; вопрос владельцу, если отчёт говорит «а он сейчас не отправляет» |
| все оставшиеся строки (N) снимает рубеж | стоп-лист, уже писали или негодное имя | разбор через `status` с `full` |
| очередь движется: отправщик берёт строки по одной с паузами | нормальный ход | ничего |

Звать владельца, не разбираясь самому, в трёх случаях: аккаунт остановлен;
`status` говорит, что держащий строки аккаунт сейчас не отправляет; в логе есть
уровень `ERROR`.

## 9. Когда что-то не так

| Симптом | Причина | Действие |
| --- | --- | --- |
| `docker compose ps` показывает `app` без `healthy`, `curl` на `:8088/health` отвечает `account stopped: ...` | Telegram ограничил аккаунт: `PEER_FLOOD`, длинный `FLOOD_WAIT` или отозванная сессия | отправка остановлена целиком и по таймеру не вернётся. Открыть аккаунт руками, посмотреть, что с ним, и только потом снимать стоп инструментом `resume_account` с меткой аккаунта. Отозванная сессия снимается не им, а повторным `make live-authorize` |
| `curl` на `:8088/health` отвечает `database: ...` | контейнер базы не поднялся | `docker compose -f docker-compose.local.yml ps`, затем `make live-up` |
| Вход печатает `telegram storage ... is locked by another process` | отправщик работает в `live` и держит файл сессии | `TRANSPORT=dry-run` в `.env`, `make live-up`, повторить вход |
| `make live-up` падает с `Bind for 127.0.0.1:8087 failed: port is already allocated` | порт занят соседним сервисом | сменить `MCP_PORT` и `HEALTH_PORT` в `.env`, поправить `url` в `.mcp.json`, `make live-up` |
| В логе `daily limit differs from env` | `ACCOUNT_DAILY_LIMIT` в `.env` не равен потолку в базе | это норма: переменная заводит потолок только при создании аккаунта, действует число из базы. Менять потолок - `runbook-account.md`, раздел 1 |
| Контейнер `app` перезапускается, в логе `load config` с ошибкой | кривое окружение, например `TRANSPORT=live is refused outside prod (ENV="dev")` | привести `.env` в порядок по таблице раздела 3 и `make live-up` |
| В Claude Code нет инструментов рассылки, `curl` на `/mcp` отвечает `401` | запись `tg-agent-mcp/mcp` в Keychain и `MCP_TOKEN` в `src/.env` разошлись | привести к одному значению и `make live-up` |

## 10. Когда одного аккаунта мало

Один аккаунт при потолке 20 писем в день даёт около сотни в неделю. Нужно
больше - к рассылке добавляется ещё аккаунт: очередь остаётся общей, каждый
аккаунт берёт из неё своих получателей, потолок и стоп считаются по каждому
отдельно, а правило «один человек - одно письмо» действует на всю кампанию.
Останавливать идущую кампанию не нужно.

Порядок из `src/`, подробно - `docs/runbook-account.md`, раздел 3:

1. скопировать `accounts/account.env.example` в `accounts/<метка>.env`, вписать
   метку, телефон второго аккаунта и ключи с my.telegram.org под этим номером;
2. `make account-up label=<метка>`, затем `make account-authorize label=<метка>`
   и ввести код из Telegram;
3. `make account-live label=<метка>`;
4. проверить: `status` показывает вторую строку аккаунта, `make accounts` -
   поднятые отправщики.

Управление и переписка остаются у главного аккаунта: у добавленного нет ни MCP,
ни диалоговых инструментов, и ответы в нём читает человек, которому он
принадлежит. Стоп по ограничению Telegram останавливает только тот аккаунт,
которого коснулся.
