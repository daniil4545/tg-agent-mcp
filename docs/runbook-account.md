# Эксплуатация рассылочного аккаунта

Три операции над живым контуром: поднять дневной потолок, заменить аккаунт
после бана и добавить ещё один аккаунт к рассылке. Все делаются руками,
инструмента MCP ни у одной нет. Первый запуск и вход в главный аккаунт -
`first-launch.md`, этот документ его не повторяет.

## Аккаунт живёт в трёх местах

| Место | Что там | Что с ним при замене |
| --- | --- | --- |
| строка `accounts` (метка из `ACCOUNT_LABEL`) | дневной потолок, стоп и его причина | заводится новая, старая остаётся навсегда |
| файл сессии в томе процесса | сессия MTProto, peer cache, состояние апдейтов | стирается: чужая сессия в хранилище вход не пускает |
| `recipients.account_id` и `direct_messages.account_id` | кто и кому уже писал | не трогается, это и есть журнал |

Том сессии зависит от того, чей это аккаунт: у главного -
`tg-agent-mcp-live_telegram_data`, у добавленного отправщика -
`tg-agent-mcp-acc-<метка>_telegram_data`.

Одна сессия MTProto живёт ровно в одном процессе, поэтому каждый аккаунт - это
свой процесс. Главный стоит в `docker-compose.local.yml` и держит MCP;
остальные поднимаются разделом 3 и управления не несут.

## 1. Поднять дневной потолок живому аккаунту

`ACCOUNT_DAILY_LIMIT` задаёт потолок только при создании строки аккаунта:
`EnsureAccount` на конфликте метки строку не переписывает, а расхождение
переменной с БД называет предупреждением `daily limit differs from env` при
старте. Значит, живому аккаунту потолок меняется в БД.

Штатный путь - команда репозитория, из корня проекта:

```
deploy/safe-ssh.sh account-limit main 20 apply
```

Без слова `apply` команда отказывается работать (`account-limit requires:
<метка> <N> apply`), а значение вне диапазона 1..40 отбивает сама обёртка.
Голый `UPDATE accounts SET daily_limit = ...` делает то же самое, но мимо этих
проверок, поэтому нужен только когда обёртка недоступна.

Что важно:

- перезапуск контура не нужен: потолок читается из БД в каждой транзакции
  выборки, и `status` показывает новое число сразу;
- правка переживает пересборку контура (`make live-up --build`) и перезапуск
  машины: она в томе `tg-agent-mcp-live_pgdata`, а не в образе;
- она не переживает потерю тома с базой. Чтобы заново поднятый с нуля контур
  не вернулся к старому числу, то же значение стоит в `ACCOUNT_DAILY_LIMIT`
  в `src/.env`, в `.env.example` и дефолтом в `docker-compose.local.yml`;
- потолок обязан быть больше нуля (`accounts_daily_limit_check`), иначе запрос
  отобьёт база.

Проверка: `status` печатает строку аккаунта «сегодня N из 20 (потолок из БД)».

## 2. Замена аккаунта после бана

Процедура собирается из существующих средств. Нового кода она не требует, но
два шага идут запросом к базе, а не инструментом.

### Что решить до начала

Замена делается **под новой меткой** `ACCOUNT_LABEL`, а не входом другого
номера под старой. Причина в рубеже: строка очереди, однажды взятая аккаунтом,
остаётся за ним и после возврата в очередь, потому что повтор доставки держится
на `random_id`, а Telegram дедуплицирует его в пределах одного аккаунта. Вход
другого номера под старой меткой оставил бы строки закреплёнными за меткой и
дал бы человеку второе сообщение молча. Под новой меткой тот же риск остаётся,
но он сведён к одной строке и снимается руками на шаге 5.

Цена решения: строка старого аккаунта остаётся в `accounts` навсегда (на неё
ссылается журнал), и `status` печатает оба аккаунта.

### Шаги

1. **Зафиксировать обстановку.** `status` через MCP: id кампании, сколько
   отправлено, что говорит строка аккаунта. Затем из `src/`: `make live-dump` -
   в базе лежит единственный экземпляр знания, кому уже писали.

2. **Остановить кампанию.** Инструмент `stop` без `cancel`: это пауза, очередь
   остаётся. С паузой отправщик не возьмёт новых строк, пока идёт замена.
   Кампания продолжится тем же `start` в конце.

3. **Подготовить контур к входу.** В `src/.env`:
   `TRANSPORT=dry-run` (в живом режиме файл сессии заперт процессом),
   `TELEGRAM_APP_ID`, `TELEGRAM_APP_HASH`, `TELEGRAM_PHONE` нового аккаунта,
   новая `ACCOUNT_LABEL`, нужный `ACCOUNT_DAILY_LIMIT`. Ключи приложения
   берутся на my.telegram.org под тем же номером, что и аккаунт.

4. **Стереть сессию старого аккаунта.** Из `src/`:

   ```
   make live-down
   docker volume rm tg-agent-mcp-live_telegram_data
   make live-up
   ```

   `make live-down` именованные тома не удаляет, база кампаний остаётся на
   месте: удаляется только том сессии. Без этого шага вход пройдёт молча на
   старой сессии, а сверка номера отобьёт его ошибкой
   `storage holds a session of another account`.

   Дальше вход: `make live-authorize`. Напечатанный номер и ник обязаны
   совпасть с новым аккаунтом; не совпали - разбираться, а не продолжать.

5. **Освободить незакрытую очередь.** Строки, взятые старым аккаунтом, новому
   недоступны: выборка берёт только `account_id IS NULL` или свой. Сначала
   посмотреть, что осталось (подставить метку старого аккаунта):

   ```
   docker compose -f docker-compose.local.yml exec -T postgres \
     psql -U tg_agent_mcp -d tg_agent_mcp -c "
     SELECT r.id, r.username, r.claimed_at, r.reason
       FROM recipients r JOIN accounts a ON a.id = r.account_id
      WHERE r.state = 'planned' AND a.label = 'СТАРАЯ_МЕТКА'
      ORDER BY r.claimed_at NULLS FIRST;"
   ```

   Строки с пустым `claimed_at` отдаются новому аккаунту без вопросов:
   сообщение по ним заведомо не уходило.

   ```
   docker compose -f docker-compose.local.yml exec -T postgres \
     psql -U tg_agent_mcp -d tg_agent_mcp -c "
     UPDATE recipients r SET account_id = NULL
       FROM accounts a
      WHERE a.id = r.account_id AND a.label = 'СТАРАЯ_МЕТКА'
        AND r.state = 'planned' AND r.claimed_at IS NULL;"
   ```

   Строка с непустым `claimed_at` - та, на которой бан застал отправку: ушло
   сообщение или нет, база не знает. По каждой такой строке решение принимает
   человек, глядя в `make live-logs` (`message sent` с этим ником) и в диалог
   старого аккаунта в Telegram. Ушло - закрыть её как отправленную:

   ```
   UPDATE recipients SET state = 'sent', sent_at = now(), claimed_at = NULL
    WHERE id = <id>;
   ```

   Не ушло - обнулить `claimed_at` и `account_id` тем же запросом, что и
   остальные. Не разобрались - оставить как есть: человек останется закрытым
   для рассылки, и это дешевле второго письма.

6. **Вернуть живой режим.** В `src/.env`: `TRANSPORT=live`, затем `make
   live-up`. Проверить: `curl -s http://127.0.0.1:8088/health` отвечает `ok`,
   в логе `service started` с `transport=live`, `status` показывает два
   аккаунта - старый и новый с нулевым расходом за сегодня.

7. **Продолжить кампанию.** Инструмент `start` по тому же `campaign_id`.
   Первое письмо уйдёт не мгновенно, а в пределах `SEND_PAUSE_MAX`: пауза - это
   весь виток отправщика.

### Что процедура не делает

- **Старый аккаунт не воскрешается.** Его строка остаётся `stopped`, и
  `resume_account` на неё звать не нужно: номер забанен, а не притормозен.
  Удалять строку нельзя - на неё ссылается журнал.
- **Дневной расход не переносится.** Новый аккаунт начинает сутки с нуля,
  даже если старый успел отправить свою порцию сегодня. Это осознанно: потолок
  стоит ради номера, а номер другой. Следить за этим в день замены руками.
- **Замена не равна добавлению.** Здесь старый аккаунт уходит с контура; чтобы
  рассылку вели несколько аккаунтов сразу, смотрите раздел 3.
- **Инструмента MCP для замены нет.** Шаги 4 и 5 идут руками. Если аккаунты
  начнут отлетать чаще раза в неделю, это первый кандидат на автоматизацию.

## 3. Добавить аккаунт к рассылке

Кампания одна, аккаунтов несколько: очередь общая, каждый берёт из неё своих
получателей, дневной потолок и стоп считаются по каждому отдельно, а правило
«один человек - одно письмо» остаётся общим на всю кампанию. Добавление идёт на
ходу: останавливать идущую кампанию не нужно.

Отправщик поднимается своим проектом поверх сети и базы основного контура, все
команды - из `src/`.

1. **Файл аккаунта.** Скопировать `accounts/account.env.example` в
   `accounts/<метка>.env`, заполнить `ACCOUNT_LABEL` (равен имени файла),
   `TELEGRAM_PHONE` и ключи `TELEGRAM_APP_ID`, `TELEGRAM_APP_HASH` с
   my.telegram.org под этим же номером: от главного контура они не
   наследуются. Метка своя у каждого аккаунта и меняться после первого
   запуска не может: к ней привязаны расход, стоп и взятые строки очереди.
   Совпадение метки с основным контуром `make` отбивает.
2. **Поднять в dry-run:** `make account-up label=<метка>`. Отправка в этом
   режиме идёт в лог, а не в Telegram: файл сессии ещё пуст.
3. **Войти в аккаунт:** `make account-authorize label=<метка>`. Telegram
   присылает код на номер, ввести его может только человек.
4. **Перевести в живой режим:** `make account-live label=<метка>`; цель пересобирает
   образ, иначе отправщик остался бы на прежнем коде. Контейнер
   пересоздаётся на той же сессии.
5. **Проверить:** `status` показывает вторую строку аккаунта с расходом и
   потолком; `make accounts` перечисляет файлы и поднятые отправщики.

Что важно:

- потолок нового аккаунта задаётся `ACCOUNT_DAILY_LIMIT` в его файле и только
  при первом старте; дальше он живёт в БД и меняется разделом 1;
- окно отправки, паузы, порог флуда и список служебных адресатов приходят из
  общего `src/.env` и обязаны совпадать у всех процессов: они участвуют в счёте
  расхода и в рубежах;
- своего адреса в сети у отправщика нет: ни MCP, ни портов наружу. Управление и
  диалоговые инструменты остаются у главного аккаунта, ответы второму аккаунту
  читает его владелец сам;
- аккаунты пишут с одного адреса, если не задан `TELEGRAM_PROXY_URL` в файле
  аккаунта;
- остановить один отправщик - `make account-down label=<метка>`; том с сессией
  при этом остаётся, и подъём продолжит работу без повторного входа. Смотреть
  его лог - `make account-logs label=<метка>`.

Стоп аккаунта по ограничению Telegram останавливает только его: соседние
аккаунты продолжают кампанию, а `status` называет остановленного и печатает
причину молчания у каждого аккаунта отдельно.
